The container take on a role of being 'eagarly reactive', or in other words... the second one of the containers or objs stored at the site, it takes the value, turns around and emits on that 4 channel and broadcasts to all call sites. Due to the nature of what we are aiming for, we already know that for each 4 channel address we are going to have many, MANY call sites listening on that address. So it makes zero sense in making the userr and in extension the fns have to be proactive and sub before getting any sort of values.

```tsx
export const SOLUTIONS = new (class {
    public t: any
	private _useRifts() {
		return root.DISRUPTOR.useSClass(this, THE_SINGULARITY_TEST, THE_SINGULARITY_SL_CH, root.DISRUPTOR.ms, root.DISRUPTOR.rt);
	}
	constructor() {
		this._metrics = new METRICS();

	}

```
> [!NOTE] 
>
> In the first example, and yes both examples have use effect in the constructor... and yes, it fucking works, sorry for letting you down and not sucking... As you can see, setting up a private, class function passing in this to start so that whatever IS available at the time of passing this whatever it may be... atleast gives us a bit of a baseline. The constructor starts up, we init our fns and assign them to thier class values, once constructor has completed its run, calling on the setter, making sure to spread the values to ensure it updates the ones we want while also adding to the pool instead of replacing the pool.
>

Also not foregetting about the fact that we ALSO have aceess to the getter, as the second method, which is the one I solely used up till now, worked just fine... but it just lacked that extra bit of surgical ergonomics and it didn't let us reach to it to use whenever we needed.
