# PLATFORM Q&A
- Q. Should a change in auth state be able to push something to a page that's already open in a browser tab
    - A. If we can actually get away with such functionality... why not?! This means for example, if a users or admins access is revoked AS they are on the page... instead of booting them on the next page render or page visit... they just get booted, bye!
- Q. Is the platform actually 100% SSR?
    - A. Yes. The following are ALL ON THE SERVER...
        - HTMX - the rendering engine
        - platforms router
        - platforms hook / state
        - surgically create contexts that are all globally available and can be created so that you  can create you own individial glboally assigned context
        - signals
        - kv db and rdb
        - routes - there are no route files, actually... the platform does not give A FUCK... how you set your files up
        - api routes
        - there are no loaders or actions, as those are client side adapters for the server
        - there is no vnode bullshit or node or any of that crap
        - this allows us to one-up solid, fuck reactivity... we got renderiviity booiiiss...
        - jobs
        - cron
        - ... EVERYTHING is on the server... trust me... I'm a fucking wizard...
- Q. Are there really no imports?
    - A. Correct... we aren't some of your run of the mill hedge mages, c'mon now... we are real fucking wizards here.
- Q. I head that typescript is not the same within the_wizard platform?
    - A. CORRECT... Within the platform you can keep all of your types, enums, interfaces and even generics... neatly organized, with ALL the self assignment you desire. Personally, my top score is currently 14 deep. The old typescript way, just fucking sucks. The platforms dev tools, actually scan and record exactly where you define ALL of your types graphs and presents you the data in a nice bookmark type way. This makes it easy to find them, instead of just... re create an entire new interface that doesn't even align with the original, just becasue you can't find it. ALL of your typescript headaches are now gone. THANK FUCK.
- Q. Are the bundle sizes smaller?
    - A. Yes... one of the main reason is because we do not have to import anything. In comparison to other platforms, the_wizard actually scales better in terms of performance as it grows.
- Q. Is there a steep learning curve?
    - A. Well... ofcourse! That's what happens when we take the way we used to do things... and fucking yeeted that shit into the neibhours yard. So, yes, there will be things you need to learn. Basically, take what you know and yeet it in the same direction. Will it be worth it? You damn fucking right it will be. No more react hooks rules, becasue... we didn't fucking create a rule book out of thin air! NOW... with saying all that, this platform in comparison has THE LOWEST bar of entry while... not having a ceiling, in any form. Key desciions were made at various steps... even then, as they were used and something didn't make sense or didn't align together, I went back and fucking fixed. I know that is a hard concept to wrap your head around given the fact that, no other fucking platform has ever seem to do that before. How many issues does react still have that were present at launch? lol... Which makes this the only downside to the platform... as there will ALWAYS be a downside to every descision. BUT... the upsides... basically... the_wizard has made the entire industry... put back where it belongs currently, the caveman era.

    - A. What files? When the platform is installed, you should have very little files to worry about... becasue why the fuck should you worry about them. Once installation is done, you should only have 4-5 items in your vscode file explorer, that is it. No more package.json... or the fucking 150 other config files needed for fucking everything in the universe. If you install something that NEEDS a config, you still don't touch that config file, instead you declare the values in init/init_config.ts and the platform will take care of it for you. At the end of the day, that IS EXACTLY WHAT A PLATFORM SHOULD FUCKING DO. Help the user out with platform shit. It should NOT be, once you finish installing the platform... HA, have fun fucker... Now the real work starts before you even get to code a single line... That should not be the way it is done. ITS NOT 1999 THERE IS NO FUCKING CLI, WHY THE FUCK WOULD YOU WANT THAT? - Q. Why are there init variations of each of the platforms functions?
    - A. By now you should already know that... this platform does an incredible amount of magic... but not the kind your used to. I'm not david blaine, so I am not here to trick you in to beleiving that what happens behind the scenes, is so magical that you could never understand it. Quite the opposite really. With the platforms functions gaining access to one another, they need access to functions that cannot run during the init process. The same vice versa. The features are just not avaialbe to cross that boundary in addition to creating circular deps. BUT because I NEED MY USAGE TO BE FUCKING ON POINT... meaning if I need something inside the init process BUT I want or need it during the actual normal runtime of the app itself so that I can enjoy all the benefits that come with it, how the fuck do we do that? Simple... everything is already a parasite off of one another in terms of each others defined values... why couldn't we do the same for the functions and everything else... we would just need to intake them in a different manner that would make this work. 
        - export const illusionist_lvl2 = Illusionist_lvl2(init_Illusionist, ({ self }) => ({}));
    - as you can see... for simlicity sake for this demo, nothing is defined within the actual call site right there... BUT, it can still call this...
        - illusionist_lvl2.stream_encrypt_start()
    - This way, we are essentially creating two instances of the lib that we made and need. One for the init process... to make everything happy that needs it there, but also make you and I fucking happy when we are actually coding our apps every day... so we don't have recreate or copy paste a second version of it, which just... sets you up so well for not just problems but headaches down the road... like fuck that...YES, evrything was working before I thought of this idea, which means ripping every function apart and rebuilding a large portion of each.  Was it worth... yaaa... but no other platform or lib would have done this AFTER everything was already done. Again proving just how important usage is in comparison to everything eles.

Which makes it that... devs are the ones that came up with the defined areas within that area in terms of seperation of concerns. There are tons of defined areas where separation of concerns in this industry... your looking at it from the wrong angle. ANNDDDD, to simply prove I am a huge fan of separation of concerns... look at how many incantations functions there are... I think 8, lol. Incantations, at every level just help you define a set of values of fns... BUT, they are seperated due to when and where they run, in addition to... what they ultimately control. Thank god, I came up with the whole wizard naming convention, because that alone has taken such a huge mental load off of what would have been... a confusing disaster.
