Previously, SClass was backed using rifts, which techncially is perfectly fine and it did work and do its job. BUT... one use case where, I'll admit I was pushing it pretty hard and I am still shocked it ended up working. 15 classes, all using the rifts storage medium as wel, no circular... tdz... init module horse shit tom foolery... Granted, just looking at the code all on its own... you would see why there weren't any issues happening but it was becasue of this redicoulous build that made me want to rebuild this idea from the ground up.

A new container / registry that ONLY specializes in serving the needs of the class fn pool... or pool of classes and their fns, and it ended up on getting code for a single fn, an emitter / broadcaster. That is it, obviously the DRS relation not just helped with this but... virtually made any issue or problem that would have given us issues... and simply eradicated it. The container take on a role of being 'eagarly reactive', or in other words... the second one of the containers or objs stored at the site, it takes the value, turns around and emits on that 4 channel and broadcasts to all call sites. Due to the nature of what we are aiming for, we already know that for each 4 channel address we are going to have many, MANY call sites listening on that address. So it makes zero sense in making the userr and in extension the fns have to be proactive and sub before getting any sort of values.

This upgrade version, also opens up SClass in an interesting way where... if we do not need all the other things that come with the SClass primitive, or maybe its shape for some reason does NOT fit exactly what we need, and I have already created the call site function for this in the same format as the other fns like useCell and so on, and we can actually take a ordinary class... and bsaicly and simply... just fucking fix it with a single paste...

Note

In the first example, and yes both examples have use effect in the constructor... and yes, it fucking works, sorry for letting you down and not sucking... As you can see, setting up a private, class function passing in this to start so that whatever IS available at the time of passing this whatever it may be... atleast gives us a bit of a baseline. The constructor starts up, we init our fns and assign them to thier class values, once constructor has completed its run, calling on the setter, making sure to spread the values to ensure it updates the ones we want while also adding to the pool instead of replacing the pool.

One benefit with this method, that the other does NOT have, is the access to the setter itself. Granting us the abiility to set and update the class pool whwnever we feel we have the need to. Also not foregetting about the fact that we ALSO have aceess to the getter, as the second method, which is the one I solely used up till now, worked just fine... but it just lacked that extra bit of surgical ergonomics and it didn't let us reach to it to use whenever we needed.
